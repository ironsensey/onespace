1. USER VISION AND PRIORITIES
-----------------------------
- OneSpace is a local-first Windows + Android ecosystem, extended with a Kali
  Raspberry Pi hub. Clipboard text/images/links, camera-photo-to-PC paste,
  encrypted files, shared workspace, device control and automation are core.
- Prioritize speed and reliability, especially Windows copied text/image to
  Android; that was the direction the user identified as slow.
- Audit existing code before changing it; preserve working behavior, identities,
  existing protocol, pairing, permissions and user data. Avoid unnecessary rewrites.
- Android/Windows should conserve battery; Pi is mains-powered but resource-poor.
- Prefer native Windows/Android experiences. The user rejected a browser-based
  Windows dashboard as the primary UI.
- Prefer application-owned routing/coordination over requiring a whole third-party
  platform such as Tailscale. Still use mature, appropriately licensed libraries,
  OS interfaces, TLS, codecs and service APIs where they are the better choice.
- Same-LAN traffic should stay direct and work without the Pi or Internet.
  Different-network access should use the Pi when direct LAN access is unavailable.
- The Windows machine may be a roaming laptop and may be switched off. The Pi,
  not Windows, is the always-on hub. Operations on an offline PC remain impossible.
- Pi camera should provide live CCTV in OneSpace. Initially recording was deferred
  because no SSD was available; user later explicitly requested recording after
  deciding to use their 5 TB Google Drive account for large storage.
- Provide temporary/permanent cloud storage, create/list/upload/delete (Trash)
  management inside OneSpace, and recording uploads to connected Google Drive.
- Keep update compatibility; automatic monotonic APK codes; avoid repeated false
  update prompts. Never uninstall the existing app to hide a signing problem.
- Add meaningful tests, logging and benchmarks. Report failures honestly.
- User likes small clear points, practical instructions and comparison tables;
  dislikes unsupported performance percentages and repeatedly asking permission.
- Inspiration mentioned: Spotify cross-device play/pause, Xiaomi interconnectivity,
  and Musixquare synchronization. No source/license adoption or measured equivalence
  to these products is established. Media commands are not sample-accurate audio sync.
- “Phydrop” appeared once in a component-comparison request; the implemented
  project/repository/package identity remains OneSpace.

5. IMPLEMENTED COMMUNICATION AND ROUTING
----------------------------------------
LAN baseline preserved:
- Windows local legacy dashboard: loopback TCP47600, authenticated local API.
  Primary dashboard is now native; -legacy-ui explicitly enables browser fallback.
- Windows paired-device API: pinned HTTPS/TCP47601, original bearer credentials.
- Existing LAN UDP discovery:47602; discovered identity must still be verified
  against paired pin. Discovery is not trusted enrollment.
- Pi scoped API: pinned HTTPS/TCP47603, optionally external443 forwarded to47603.
- Route priority: verified local PC LAN -> optional existing approved overlay ->
  discovery/reselection -> explicitly enabled OneSpace built-in Pi relay.
- Direct LAN stays independent of Pi and Internet. Pi-only functionality requires Pi.

Built-in OneSpace Connect (new):
- No mandatory separate Tailscale application/account.
- Windows makes outbound persistent receiver connections to Pi, so laptop may move.
- POST /hub/v1/connect/listen registers a receiver.
- POST /hub/v1/connect/open?to=DEVICE opens a connection to enrolled device ID.
- Both require connect scope, bodyless HTTP/1.1 Upgrade,
  Connection: Upgrade, Upgrade: onespace-connect-v1, successful status101.
- Receiver waits for byte0x01, then acts as original PC TLS server.
- Original PC TLS session is carried INSIDE pinned Pi TLS. Android verifies PC
  separately and sends original PC token/password only inside the inner TLS.
- Pi forwards encrypted PC bytes and cannot read inner PC clipboard/files/password.
  Pi can observe connection metadata and still terminates outer TLS.
- Hub only joins enrolled receivers; never opens arbitrary client-supplied URLs/IPs.
- Four Windows reverse workers; LIFO receivers favor fresh connections.
-10 sockets/device,32 total; idle receiver15min; activepair1h; slidingI/O90sec.
-32KiB bounded copy buffers per direction, no whole-file Pi staging.
- Revocation/scope removal checked every second; hub shutdown closes connections.
- Windows uses OS interface/address change notifications +500ms debounce,
  and resume notifications; no continuous IP-address polling loop.
- Windows private Pi address preflight800ms, remote4sec, local failure cooldown30sec.
- Android route cache30sec keyed to identity/network/profile, failure invalidation.
- Never replay an uncertain modifying request through another route automatically.

Other Pi event route:
- Event-woken long polling for short clipboard text and media commands.
- Separate trusted-Pi queue, NOT inner-PC end-to-end encryption.
- Pi can read/store queued text until acknowledged/expired/purged.
- Shared queue256; server text64KiB, client policy16KiB; enrolled devices128.
- Clipboard60sec expiry, media15sec, sweep5sec; explicit recipient ACK.
- New pending text same sender/recipient replaces older pending text.
- Stable IDs/idempotency reduce duplicates, but no exactly-once OS-action promise.
- Windows default copied-text route remains lan (original PC API), which may run
  through encrypted Pi connection. Explicit hub route is a different trust choice.

Reachability boundary:
- This is NOT a general ICE/STUN/TURN data transport or a hosted public relay.
- Pi must be reachable from both networks: publicIPv6 or publicIPv4+portforward/DNS,
  or another separately provisioned reachable endpoint.
- CGNAT cannot be fixed merely by installing this app. No endpoint was provisioned.
- Pi private ingress default. Explicit --allow-public / ONESPACE_ALLOW_PUBLIC=true
  needed for public clients.128 total/16-per-IP ingress caps before TLS.
- Never publicly expose Windows47601. Keep scope/auth/firewall restrictions.
- Optional Pi LAN address shares same certificate pin, avoiding hairpin NAT issues.
- Tailscale/WireGuard remains optional compatibility, not bundled/required.

9. DRIVE, RECORDING AND STORAGE
-------------------------------
- Google Drive uses the user's 5 TB account. Signing in with the Gmail identity
  grants Drive access; no Gmail inbox-reading permission is requested.
- Own Desktop OAuth client, PKCE, state-checked loopback callback, drive.file scope.
  Headless Pi consent can use SSH callback forwarding. No real account was set up here.
- Tokens and resumable URLs are protected owner-only metadata, never UI/log output.
- Manage only OneSpace-marked files in the verified app folder, not unrelated files.
- Temporary storage defaults to 7 days, configurable 1–365; permanent until deletion.
  The original handoff's five-day maximum was a historical design. Confirm desired
  policy before changing current retention behavior.
- List, create, upload, resume and move to Trash in OneSpace. Trash normally keeps
  quota occupied until Google's later purge (usually 30 days) or manual emptying.
- Resumable uploads use 1 MiB chunks, fixed Google endpoints, strict session URL
  checks and preallocated Drive IDs to reduce ambiguous-completion duplicates.
- Existing H.264 stream produces roughly 15-second finalized fMP4 segments. Remote
  MD5 is verified before local deletion; MD5 is an integrity check, not encryption.
- “Direct to Drive” means a bounded local spool followed by verified upload. It
  does not mean zero SD writes or unlimited recording during an Internet outage.
- Recording spool: 128 MiB ext4 image on SD, not tmpfs/RAM; pause around 96 MiB or
  below 8 MiB free. Keep at least 512 MiB free outside it. Outages can cause gaps.
- 5 Mbps is about 54 GB/day; 5 TB about 92 days before other usage/Trash. Estimate.
- Ordinary Google-readable files/MP4s, not an end-to-end encrypted cloud vault.
- systemd memory ceilings: hub160 MiB, MediaMTX192 MiB, camera320 MiB. Ceilings
  are not allocations or measured RSS. Real Pi memory/power/thermal tests remain.

10. APK UPDATES AND MONOTONIC VERSION AUTHORITY
----------------------------------------------
- Original Windows update protocol retained; Pi hosts updates so PC may be off.
- GET /hub/v1/updates/manifest and /apk require updates scope.
- PUT /hub/v1/updates/apk and POST /hub/v1/updates/reserve require updates.publish.
- Strict binary AndroidManifest parser, package allowlist, 150 MiB cap, streaming,
  periodic sync every 4 MiB, SHA-256, immutable names and atomic manifest.
- Reject code <= published release; refuse corrupt metadata overwrite; clean old
  APK only after successful publication. Publisher does NOT verify APK signature.
- Android verifies bytes/hash/size/package/code and installed signer continuity;
  the OS installer independently verifies and requires user approval.
- Manifest keeps /v1/update/apk downloadPath; adapter maps to the fixed hub route.
- Shared counter is serialized, file-locked, durable and monotonic over restart.
  Maximum code 2.1 billion. Failed builds may leave gaps; never reuse reservations.
- Local counters coordinate only one machine. Multiple builders need ONE authority.
- Optional Gradle environment, kept private:
  ONESPACE_SHARED_VERSION_CODES=true
  ONESPACE_HUB_URL=https://YOUR_PI:47603
  ONESPACE_HUB_FINGERPRINT=VERIFIED_64_HEX_PIN
  ONESPACE_HUB_TOKEN=PRIVATE_PUBLISHER_TOKEN
- Explicit assemble/bundle/install reserves; IDE sync does not. An unavailable
  authority fails rather than silently falling back to an uncoordinated counter.
- tools/reserve-android-version.py provides pinned allocation and a build helper.
  Already reserved code: -PonespaceVersionCode=N avoids a second allocation.
- Data-preserving rollback: older source + same key + NEW higher code, not downgrade.

remote-outbound-rtp and transport reports — no candidate-pair, local-candidate
or remote-candidate reports — and its ICE gatherer hardcodes aioice
TransportPolicy.ALL. Therefore it cannot force relay-only selection and cannot
report the selected pair's candidateType. A decoded frame alone does NOT prove
the selected media path was relayed; merely configuring a TURN URL or seeing a
coturn allocation is insufficient.

  and RTCIceTransport.getSelectedCandidatePair() (selected pair candidate types).

  fails unless the selected pair is relay/relay. TLS verification, coordinator
  authorization, non-trickle ICE, offer/answer through the coordinator, and
  session cleanup are unchanged.
- Dockerfile.receiver now builds node:20-slim + playwright@1.48.0 + chromium
  (with deps); docker-compose receiver runs `sleep 8; exec node /receiver.js`.

9. CONNECTION ENGINE — OPERATING MODES
--------------------------------------
- Mode A / LOCAL DIRECT: First attempt existing authenticated UDP LAN discovery and direct HTTPS 47601 transfer/clipboard. If local candidate proves reachable and trusted, choose it. Bypass Pi for large peer-to-peer payloads. Hub remains registration/presence authority when online; apps still interoperate when hub down.
- Mode B / REMOTE DIRECT: When peers are on different networks, establish encrypted overlay/remote P2P to trusted device endpoints, not plain port-forwarded HTTP. Use end-to-end authenticated sessions, dynamic IP handling and permission checks.
- Mode C / REMOTE RELAY: If NAT/firewalls prevent direct connection, fall back to encrypted relay service. Relay may carry ciphertext; it should not decrypt payload content when designing E2E app-level messages. May be slower and consume external bandwidth.
- Mode D / STORE AND FORWARD: If recipient offline, keep bounded encrypted event/task/small-file jobs in hub if policy allows; deliver after reconnect with stable IDs and dedup, expiry, quotas, retry/backoff. Never pretend delivered when only queued.
- Device selection should be automatic: network change/IP change triggers reconnection; authenticated health status, transport latency/throughput, metered policy, battery mode and rights inform path choice. Hysteresis to prevent rapid flapping. Continuous fallback; transparent UI path label ('LAN Direct', 'Remote P2P', 'Relay', 'Offline').
- Tailscale first for deployment proof (Pi, Windows, Android clients) with existing WireGuard-based tunnel; Tailscale still uses external coordination/relay as needed. User wants eventually fully integrated OneSpace Anywhere UI without separate manual VPN app. Could explore self-hosted coordinator/Headscale later but that still needs reachable infrastructure. Avoid prematurely building cryptography/NAT engine from scratch without extensive tests.
- Pi behind NAT/CGNAT may not be internet reachable. The hub alone cannot magically provide universal remote access; use an existing secure mesh or dedicated reachable coordination/relay node. Self-hosted relay on home Pi alone is not sufficient behind CGNAT.
- LAN-only operation must never depend on reachability to Tailscale or internet.
- Remote app features remain limited by OS APIs (clipboard/camera background policies, power control privileges); remote connectivity does not grant OS capabilities.

14. SMART VIDEO STORAGE — THREE OPTIONS PLUS ARCHIVE COMPRESSION
-----------------------------------------------------------------
[PLANNED, USER REQUESTED STORE SMALLER WHILE LIVE REMAINS UNCHANGED]
A. CONTINUOUS (highest completeness): capture all H264 from single encoder, 5-day max/quota oldest-first. Full scene coverage; 270GB/5d at actual average 5Mbps.
B. MOTION ONLY: keep full-quality video when motion detected, with e.g. 10s pre-roll in bounded memory/storage ring and 30s post-event recording; can miss motion, false triggers, or slow/quiet events. Requires a real event detector and safe segment selection; not a one-line toggle in MediaMTX.
C. TIME-LAPSE ONLY: during quiet periods save one image every configurable 2/5/10/30 seconds rather than 46fps. Huge storage reduction BUT loses all movement between snapshots, cannot reconstruct full surveillance. Do not advertise as continuous coverage.
D. SMART HYBRID (USER-FAVORED PROPOSED MODE): motion → original quality video; idle → low-frequency snapshots; optionally retain short low-fps recording if capacity permits; provide timeline of video clips and snapshots. Even if user asks 'no quality loss' make explicit: full event clips can be unmodified, but skipped idle moments are not recorded.
E. AFTER-THE-FACT TRANSCODING: Windows PC when available can convert completed segments to H265/AV1 to reduce file size at roughly comparable perceived quality, then hashes/playback verified and originals only removed after safe verified commit. This is lossy re-encoding and resource-intensive; Pi3 should NOT try heavy H265/AV1 in real time. Windows worker OPTIONAL, no Windows requirement for live/recording.
F. VARIABLE BITRATE: hardware H264 encoder might support VBR, but must inspect v4l2 controls. Reduces bits for static scenes while preserving detail as configured, actual size scene-dependent. Higher bitrate generally reduces blockiness but increases disk usage/network; 5Mbps confirmed subjectively sharp/smooth.
G. RECORDING SCHEDULES: allow hours/day/weekday windows, record on-demand, exports before expiry, user setting max 5d and per-camera quotas.
- Illustrative 5d saving example: 10% of time at 5Mbps + 50KB snapshot every 5 seconds for remaining 90% ~27GB video +3.89GB snapshots = ~31GB, vs 270GB. Not a guarantee; motion frequency and snapshot size unknown.
- Example time-lapse JPEG every 5s @50KB: 864000s /5 = 86400 pictures over five days? CORRECT calculation: 5 days 432000 seconds /5 = 86400 pictures; at 50KB each ~4.32GB for ALL-IDLE 5d. Hybrid with 90% idle ~3.89GB.
- Do not fire two simultaneous libcamera clients if pipeline does not support; branch after the one hardware-encoded stream and/or use low-fps downsample for motion detection carefully. On Pi3 motion detection must be sparse/light (e.g. downscaled grayscale sampling) or delegated to Windows worker; avoid making camera recording lag.
- User explicitly asked to understand 'packet' CCTV recording. Explain: network packets vs compressed I/P frames vs timed MP4 segments; normal NVRs continuously segment and use overwrite-on-full; neither segmenting nor re-mux by itself saves storage.

## 1. Get the files and preserve identity

```sh
git clone --branch dev/onespace-independent-connect --single-branch https://github.com/ironsensey/onespace.git
cd onespace
sha256sum -c SHA256SUMS.txt
```

Keep Windows `%AppData%\OneSpace` (or your custom data folder), the stopped Pi's
`/var/lib/onespace-hub`, and the original Android signing key. Use the same
`com.onespace.companion` package. Do not uninstall Android to bypass a signer
error. The Pi is the documented Kali aarch64/ARM64 Pi 3 with 1 GB RAM.
Fix the previously reported undervoltage before relying on camera operation.

## 2. Install the Pi hub

Skip the stop command on a first installation. Commands below run in the
extracted project root on the Pi:

```sh
sudo systemctl stop onespace-hub.service
sudo sh hub/deploy/install-hub.sh bin/onespace-hub-linux-arm64
```

For recording, inspect and run this FIRST-TIME ONLY script while stopped:

```sh
sudo sh hub/deploy/setup-recording-buffer.sh
```

It creates a 128 MiB ext4 image on the SD card, not in RAM. It refuses an
existing image/recordings. Install e2fsprogs/util-linux if tools are missing.
Never delete an existing image containing footage. Keep at least 512 MiB free
outside the buffer and space for the published APK. Outages can fill the buffer
and cause gaps; it is not long-term offline recording storage.

## 3. Choose reachable Pi addresses

Edit `/etc/onespace-hub/hub.env` after installation. For LAN-only testing, use
your Pi LAN address; loopback 127.0.0.1 is unreachable from other devices.
An all-interface example is:

```text
ONESPACE_LISTEN=0.0.0.0:47603
ONESPACE_ALLOW_PUBLIC=false
ONESPACE_CAMERA_UPSTREAM=http://127.0.0.1:8889/camera/whep
```

Restrict the listener with your OS firewall. For remote access without a VPN,
the Pi needs public IPv6 reachability or a suitable public IPv4/router port
forward for TCP 47603. Set `ONESPACE_ALLOW_PUBLIC=true` only for that deliberate
deployment. Ingress has connection caps, but a public deployment still needs
firewall rules, OS updates and security testing. Forwarded headers never grant
access. Do not expose 47601 on the Windows laptop publicly.

**Carrier NAT cannot be fixed by this ZIP.** If your ISP gives no reachable
address, ask about a public address/IPv6, or provide another reachable relay.
No hosted endpoint, router change or DNS name is created automatically.
Tailscale remains an optional compatibility route, not a requirement.

Use a stable DNS name if your public address changes. Both apps support an
optional Pi LAN address with the SAME certificate pin, allowing local access
when the router cannot loop public traffic back into your LAN. Windows still
uses outbound connections to the Pi when it moves to another network.

## 4. Grant device scopes while the hub is stopped

```sh
sudo -u onespace-hub /opt/onespace-hub/bin/onespace-hub enroll --data /var/lib/onespace-hub --id windows --name 'My PC' --kind windows --scopes clipboard,media,camera,cloud,recording,connect,updates,updates.publish
```

For EXISTING IDs, retain tokens and explicitly replace their scope lists:

```sh
sudo -u onespace-hub /opt/onespace-hub/bin/onespace-hub permissions --data /var/lib/onespace-hub --id windows --scopes clipboard,media,camera,cloud,recording,connect,updates,updates.publish
sudo -u onespace-hub /opt/onespace-hub/bin/onespace-hub permissions --data /var/lib/onespace-hub --id phone --scopes clipboard,media,camera,cloud,recording,connect,updates
```

Grant only what you need. `connect` is required on BOTH relay devices. It does
not grant PC pairing or override PC permissions. `updates` downloads APKs;
`updates.publish` publishes APKs/reserves version codes. Do not grant publishing
to ordinary receiving devices. Revoked devices cannot be revived by a scope change.
Inspect the Pi's identity through your trusted local/SSH console:


# v0.8.0 Drive and recording additions

- New authenticated `/hub/v1/cloud/*` routes are separate from the original LAN protocol.
- `cloud` is a new explicit device scope; recording additionally requires `camera` and `recording`.
- Native Windows local routes retain their loopback/Host/X-Local-Key gate and the pinned hub credential. Android uses exact certificate pinning and a non-exported protected activity.
- Google OAuth Desktop flow requests only `drive.file`, uses PKCE and a state-checked loopback callback. Tokens and resumable URLs are owner-only Pi metadata, never UI fields.

- Only OneSpace-marked files in the verified app folder may be managed; unrelated Drive files and folders are rejected.
- Uploaded MP4s are ordinary Google-readable files. TLS protects transport; the Pi and Google are trusted storage endpoints. No end-to-end cloud encryption is claimed.
- The 128 MiB ext4 loop image caps recording disk consumption independently of hub health. Software pauses around 96 MiB; MediaMTX part buffering is capped at 8 MiB. Disk/CPU/RAM behavior on the Pi remains to be measured.
- Checksums verify completed recording bytes before local deletion. MD5 here matches Drive's integrity checksum; it is not used for authentication or encryption.
- Temporary cleanup queries indexed expiry-day properties and catches up from a durable date cursor. Trash is recoverable initially and continues consuming Google quota.
- Large user files are forwarded in bounded chunks; Android uploads are foreground-only, cancellable, and request consent on metered networks.

|---|---|---|
| Existing Windows ↔ Android LAN sharing | Existing pinned HTTPS API on TCP 47601 and UDP discovery on 47602 | Independent of Pi and Internet |
| Direct access through an approved private overlay | Existing pinned OneSpace endpoint over a separately installed overlay | Both endpoint devices must be online; explicit overlay admission is required |
| Pi clipboard broker | Pinned HTTPS on TCP 47603, scoped bearer credentials and event-woken long polling | Text messages only in this initial broker protocol |
| Pi media command broker | Same scoped event protocol | Target must consent and be online to execute; commands expire quickly |
| Live camera signaling | Authenticated WHEP SDP through the Pi hub to fixed loopback MediaMTX | Camera viewing permission required |
| Live camera video | WebRTC media to MediaMTX, with ICE connectivity through the LAN/private overlay | HTTP page/signaling reachability alone does not prove media reachability |
| Camera recording, retention and playback archive | Deferred | Not implemented or enabled in this preview |

Tailscale/WireGuard is an optional deployment layer, not an embedded VPN or a replacement for OneSpace authorization. Tailscale may use external coordination and relay infrastructure. A private tunnel does not automatically permit a device to copy a clipboard, view the camera, or control media. Headscale/custom relay infrastructure and automatic universal NAT traversal are outside this preview.

## Hub identity and enrollment

The hub has its own TLS identity, stored separately from every existing Windows identity. Verify its SHA-256 certificate fingerprint through a trusted local channel before saving a client profile. Do not accept a fingerprint supplied only by an untrusted discovery response. Damaged existing identity files must produce an error, not silent key regeneration.

Provision hub devices using the local administrative CLI. Enrollment credentials are sensitive and should be transferred only through a trusted local channel. Hub API credentials are scoped, unique per enrolled device, and must not be shared across Windows and Android. Unspecified new hub scopes are denied. Existing legacy pairing and its storage remain separate from hub enrollment.

The public hub information endpoint establishes neither pairing nor readiness. Device presence is based on recent authenticated activity and can lag an abrupt network loss. The interface must distinguish stored pairing, reachable service, active camera publisher, and actual decoded frames.

## Event delivery

The hub event API uses stable caller-supplied operation IDs for idempotency, a bounded shared queue with recipient-specific delivery, expiration and explicit recipient acknowledgements. A successful enqueue means queued; it does not mean the recipient pasted the text or executed the command. An acknowledgement records recipient processing, not proof that a third-party app accepted a paste. The initial queue limit is 256 events total, 128 enrolled devices, and 64 KiB per server text event; the client UI/sender policy is tighter at 16 KiB. New pending clipboard text from the same sender to the same recipient replaces older pending text. A single device can exhaust the shared queue with other permitted work, so quotas per sender remain a future improvement.

Clipboard and media commands have different lifetimes. A stale clipboard must not unexpectedly replace current user content, and a delayed media command must not execute minutes later. Receiver-side feature switches and platform permissions remain authoritative even if hub authorization succeeds. Clients must not automatically replay an uncertain legacy POST through a different transport and claim exactly-once delivery.

The default copied-text route remains the existing LAN route. The preview exposes an explicit hub route rather than replaying uncertain legacy writes through both routes. Media dispatch is best effort with at-most-once receipt-before-action handling: a crash between that receipt and an OS action can lose a command. The protocol does not promise exactly-once operating-system actions. Durable message queues are not a distributed consistency service for tasks/notes in this preview. File relay, resumable brokered image/file transfer, conflict-free notes and distributed release-code allocation remain future work.

## Encryption and storage

Each client-to-hub connection is encrypted and authenticated using the pinned hub certificate and a scoped credential. WebRTC encrypts the media transport. These protections are not a claim that the hub is blind to content: it terminates TLS, processes brokered clipboard text, and runs MediaMTX as the camera endpoint.

This initial hub uses bounded local metadata storage rather than a heavy service framework. Clipboard event payloads may exist as plaintext in that protected state file until acknowledged/expired and purged. Clipboard events expire after 60 seconds, media commands after 15 seconds; idle expiry is swept every five seconds. Digest-only idempotency receipts remain briefly after delivery. Filesystem permissions, short retention and bounded queues reduce exposure; they do not replace disk encryption. Do not describe the broker as end-to-end encrypted between Windows and Android or zero knowledge. Host compromise can expose clipboard text and camera video.

Android hub credentials use a separate Android Keystore-backed profile. The existing PC profile, Keystore alias and application ID remain compatible. Windows hub credentials use per-user DPAPI protection and must never appear in a dashboard response or logs. The non-Windows development adapter is base64 in an owner-only file, not an OS vault; it is not intended as protected Linux desktop credential storage. Certificate fingerprints are public identity checks; bearer tokens and private keys are secrets. Changing the Windows hub address or fingerprint requires supplying its new scoped credential rather than forwarding the old one to a different endpoint.

## Camera boundary

Only the configured loopback MediaMTX WHEP endpoint may receive forwarded signaling. A client cannot choose an arbitrary upstream URL. The gateway must reject redirects, oversized SDP, cross-origin session locations and deletion of another device's session. It should bind a session to the same enrolled device and require current camera scope for further operations.

Authorization on initial WHEP creation alone does not revoke an already established video session. The gateway revalidates sessions every 15 seconds and requests upstream deletion for revoked/expired sessions; network failure can delay actual upstream teardown. The default session lifetime is one hour and the Pi-oriented default permits two viewers. Graceful shutdown deletes known sessions. An abrupt crash can prevent this cleanup, so restarting the upstream media service may be necessary. Do not assume closing the OneSpace signaling page instantly stops an independent WebRTC connection.

Keep RTSP publishing and MediaMTX management private. Permit only required media ports on a trusted LAN/overlay, disable unused listeners, and preserve the user-tested single-capture/single-encoder pipeline. No SD-card recording is configured in this preview. “Recording disabled” does not imply that no control metadata or bounded logs are written.

## Platform and verification limits

Android 10+ background clipboard restrictions, service lifecycle limits, battery policies and user force-stop remain in force. Opening a remote tunnel does not grant background clipboard reading or silent power control. Live playback should stop when its screen closes and must not silently acquire microphone or camera permissions.

The supplied automated checks exercise local server protocols, negative authorization cases and pure policy logic. Linux clipboard stubs cannot validate Windows clipboard behavior. A fake WHEP upstream can validate signaling routing and ownership checks, not real camera encoding, ICE connectivity, delivered FPS or Android WebView decoding. Pi ARM64 compilation does not demonstrate execution on the physical Pi.

Before treating the build as a stable deployment, test the actual Pi power health, camera pipeline, overlays on different networks, native Windows clipboard/media execution, Android background behavior, same-key APK upgrades and disconnect/revocation recovery. No zero-bug, zero-latency or measured battery-improvement claim is made.

## v0.9.0 OneSpace Connect and Pi update service

The built-in PC relay requires no VPN application. It uses HTTP/1.1 Upgrade
inside exact-pinned hub TLS, then carries the original independently pinned PC
TLS connection. No new cryptographic algorithm or unauthenticated arbitrary-host
proxy is introduced. The Pi cannot read the PC password, bearer token or file
contents in that inner connection. The existing short hub-text queue remains a
separate trusted-Pi plaintext queue; do not confuse its security properties.

- POST /hub/v1/connect/listen registers an outbound receiving connection.
- POST /hub/v1/connect/open?to=DEVICE selects an enrolled receiver, never an IP.
- Both sides require connect scope. Requests need bodyless HTTP/1.1, Connection:
  Upgrade and Upgrade: onespace-connect-v1. Success returns 101.
- A receiver waits for a single byte 0x01 before starting its PC TLS server.
  The sender immediately starts its PC TLS client after its 101 response.
- At most 10 sockets per device and 32 total. Receivers expire after 15 minutes;
  active pairs expire after one hour and have sliding 90-second I/O limits.
- Revocation/scope removal is rechecked every second; closing the hub closes
  its hijacked connections. Relay buffers are bounded, without file staging.
- Windows uses four workers and kernel network/address-change notifications.
  Normal shutdown, profile changes and resume rebuild outbound connections.
- Android selects and verifies a route before writes. OkHttp retries and
  redirects are disabled. An uncertain POST/upload is not automatically replayed.
  A connection failure invalidates its route cache; reads may recover safely.
- The Pi remains private-ingress-only unless --allow-public is explicitly set.
  Opt-in public ingress has 128 total sockets and 16 per IP, before TLS. Firewall
  and public reachability remain deployment responsibilities. No hosted relay,
  automatic router configuration, STUN/TURN service or NAT guarantee is supplied.

Pi updates: GET /hub/v1/updates/manifest and /apk require updates scope.
PUT /hub/v1/updates/apk and POST /hub/v1/updates/reserve require updates.publish.
APKs are capped at 150 MiB. Package/version metadata is parsed from compiled
AndroidManifest.xml; bytes are SHA-256 hashed. Publication is atomic and rejects
codes <= the current release. This publisher does not verify the APK signature;
only trusted publishers may submit. Android still compares the archive signer
to its installed signer and requires the OS installer's final approval.
The manifest retains the existing /v1/update/apk downloadPath contract; Android's
selected transport maps it to the fixed hub endpoint rather than trusting a URL.

The shared version counter is serialized, fsynced and monotonic across restart.
Use one authority and the actual published floor on all builders. Local counters
alone do not coordinate multiple independent release machines.

The native Windows UI retains the authenticated local handlers in-process.
The video component is isolated in a child process, uses fixed local content,
denies browser permissions, blocks external web resources, and requires a
per-viewer random proof for camera RPC. Hub tokens never enter its document.
The locally vendored WebView2 wrapper adds only a constructor configuration hook;
its upstream licences and loader notices are retained. Native UI/device execution
and deployment security checks are still required before a production release.

# OneSpace security notes — developer prototype

## Implemented protections

- Android manually pins the **SHA-256 fingerprint of the Windows TLS certificate**. The Android client checks the certificate hash and expiry before transmitting the ecosystem password or sharing data. A user must copy and verify the fingerprint from the trusted Windows PC, *not from an unsolicited network message*.
- Password authentication is performed inside that certificate-pinned encrypted channel. The desktop stores a salted PBKDF2-HMAC-SHA256 password verifier (200,000 iterations), never a plaintext password. Pairing is rate limited and requires an approval on the Windows dashboard.
- Every approved Android instance receives a 256-bit random bearer credential. Android encrypts its credential using a key generated by Android Keystore; Windows stores its pairing data in the current user's profile directory, where standard Windows user permissions apply.
- The LAN service refuses non-private source IPs and exposes only TLS on port 47601. The local web dashboard is bound to loopback 127.0.0.1:47600, requires a secret per-process header for API calls, and does not grant CORS access to third-party websites.
- Windows remote power commands are opt-in, queued for confirmation on the PC, expire after two minutes and cannot force-close unsaved documents directly through an untrusted phone connection.
- Uploaded filenames are sanitized, and path-based download operations use server-owned file metadata rather than untrusted paths.

## Before any public release

- **Do a real security review and penetration test.** Encryption and unit tests do not prove the software is bug-free or suitable for sensitive enterprise data.
- Encrypt the stored Windows device tokens at rest with DPAPI or another OS-provided key store (in 0.1.0, app data under the user's profile contains persisted bearer tokens).
- Implement secure credential rotation, recovery, certificate renewal, onboarding QR code with independent authentication, and device permission granularity.
- Improve network threat model for proxying and local network segmentation. Never open the LAN service to the public internet without a properly designed relay/identity protocol.
- Audit software supply chain and reproducible builds; obtain executable and APK signing certificates for production.
- Verify idle wakeups, scoped storage policies, BLE access, clipboard and background service restrictions on actual Android releases.

## Android platform limits

- Modern Android restricts background clipboard access and automatically running long-term foreground data-sync services. The present companion performs clipboard actions explicitly from its UI or Android Share menu. Capturing within OneSpace is supported as a workflow; intercepting every external camera shot indefinitely is not promised.
- Ordinary Android apps cannot silently enable Bluetooth on modern versions or simply reuse another host's Bluetooth pairing by copying a MAC address.
- Ordinary third-party apps cannot silently shut down/reboot a personal Android handset. We intentionally do not offer unsupported privilege-escalation methods.


## Local APK updates (new preview)

- Windows desktop Update Center requires its local authorization key to upload an APK. Remote endpoints require an enrolled Android device bearer token and TLS, plus the Android client pins the PC certificate fingerprint.
- Windows limits updates to 150 MiB, computes SHA-256 and publishes immutable metadata for the current update while protecting reads and writes with an update lock. Windows checks a ZIP header, **not** the APK signature: the APK must be from a trusted release process.
- Android downloads in chunks into a temporary file, checks the hash, file size, package name, version code, and archive signing certificates against the installed app before requesting OS installation. Android performs its own independent final package-signature check and requires user approval.
- The update mechanism supports the current signing identity, but does not yet support APK signing-key rotation. Keep the same `.jks` key for all builds.
- The current dashboard does not validate APK signature or version metadata itself. Never publish untrusted content. Compromised Windows credentials or a stolen signing key are outside the protections of ordinary TLS transport.

## v0.9.0 development boundary

See docs/PROTOCOL-AND-SECURITY.md for the opt-in built-in relay/public ingress,
separate update-publisher scope, nested PC TLS and isolated video-component model.
This preview has not had a penetration test. The Go vulnerability database was
inaccessible in the cloud workspace, so dependency scanning is not marked passed.
The branch-limited GitHub Actions security job can run from a permitted network.
Existing Windows PC pairing tokens retain the original profile format and OS
user-file protection; the newer hub token uses DPAPI. No blanket claim that all
old profile secrets are encrypted at rest is made. Preserve private backups and
use appropriate operating-system account/disk protections.

# Google Drive storage and camera recording · v0.8.0 preview

This package adds Google Drive integration to the existing OneSpace preview.
It does not sign into, upload to, or modify your actual account until you
configure and run it. Your Gmail address identifies your Google account;
OneSpace does not request permission to read Gmail.

## What you get

- Windows: **Cloud & recordings** in the dashboard.
- Android: **Pi Hub → Cloud storage & recordings**, behind device unlock.
- Upload large files, create text files, view the app's Drive files, open them
  in Google Drive, change Temporary/Permanent policy, and move files to Trash.
- Resume a file by selecting the same original filename, size **and contents**.
  The source file remains on the sending device. Pending sessions belong to
  the device token that started them; each device sees only its own file jobs.
- Record the existing Pi camera stream into short H.264 MP4 segments and
  upload completed segments to Drive. Live view remains available.
- A seven-day temporary default, adjustable from 1–365 days. The lifetime starts after upload verification. Existing files
  retain their policy until explicitly changed. Permanent means keep until
  you delete; it does not mean immutable or immune to Google account policies.

## 1. Preserve your installation

- Keep the previous package as a rollback copy.
- Back up the stopped hub's `/var/lib/onespace-hub` securely, including its
  certificate, device records, and any pending clips. Do not share this backup.
- Keep Windows `%AppData%\OneSpace`, its identities and pairing data.
- Build Android with your **original release signing key**, same application ID
  `com.onespace.companion`, and a code above your actual installed/published
  maximum. This source starts at code 18; refresh the published floor if your
  real app is newer. Cloud-built debug signing is not a compatible update.
- This branch extends the source available here; later unprovided v0.11/v2
  source is not included or overwritten.

## 2. Install the hub and bounded recording buffer

Use the ARM64 binary for the documented aarch64 Kali installation. Check the
Pi's power supply first: previously reported `get_throttled=0x50005` indicates
an active power/throttling problem. Recording cannot repair undervoltage.

```sh
sudo systemctl stop onespace-hub.service
sudo ./hub/deploy/install-hub.sh ./bin/onespace-hub-linux-arm64
sudo ./hub/deploy/setup-recording-buffer.sh
```

The buffer setup is a **first-time, opt-in root script**. Read it first. It
creates a new 128 MiB image file on the SD card, formats that file as ext4, and
mounts it at `/var/lib/onespace-hub/drive/spool`. It never formats a disk or
partition, refuses an existing image, and refuses to hide existing footage.
It also makes hub startup depend on the mount. Install `e2fsprogs`/`util-linux`
if their tools are missing. Keep at least 512 MiB free outside this image.

This is a hard filesystem capacity limit, not 128 MiB of Pi RAM. It bounds SD
usage even if the hub crashes or recording control fails. The hub normally
pauses near 96 MiB buffered or below 8 MiB available in the buffer. It requires
a distinct 64–256 MiB recording filesystem before enabling recording; you can
provision an equivalent filesystem yourself instead of running the script.

Do not put backups, Google credentials, or other user files inside this mount.
Do not run the setup script on every update. A failed setup is reported and
does not start recording. Review any partial installation before retrying;
never delete an existing image that may hold footage.

## 3. Configure MediaMTX without changing capture

- Keep your existing OV5647/libcamera hardware capture command unchanged; it
  still publishes `rtsp://127.0.0.1:8554/camera`.
- Review `hub/deploy/mediamtx-drive-recording.example.yml` against your actual
  MediaMTX v1.21.2 configuration. Save a backup before installing it.
- The example starts with `record: false`. It enables the management API only
  on `127.0.0.1:9997`, and grants API/publish/read only to loopback callers.
- Preserve your reachable WebRTC LAN/Tailscale ICE host configuration.
- Install the reviewed example as `/etc/onespace-hub/mediamtx.yml` only after
  checking your existing settings. Recording output and the completion hook
  must match `/var/lib/onespace-hub/drive/spool/camera`.
- If using our systemd examples, review `onespace-mediamtx-drive.service` and
  install it **as the existing `onespace-mediamtx.service`**, not as a second
  competing MediaMTX service. Back up that unit first.
- This optional transport unit runs as `onespace-hub` so it can write the
  owner-only buffer. The camera capture service remains separate. Do not run
  two MediaMTX processes on the same ports.
- The recording transport depends on the hub: stopping/restarting the hub
  also stops it. Start MediaMTX again after hub maintenance. This safeguards
  recording lifecycle; the hard filesystem cap provides independent protection.

Do not expose RTSP, the management API, or raw WHEP signaling on public
interfaces. Keep HTTPS 47603/WebRTC media limited to trusted LAN/overlay peers.
The existing live-only example remains available if you disable recording.

## 4. Create your own Google OAuth client

1. Open [Google Cloud Console](https://console.cloud.google.com/), create or
   select a project, and enable **Google Drive API**.
2. Configure Google Auth Platform consent for your personal application.
   During Testing, add your own Google email as a test user.
3. Create an OAuth client of type **Desktop app**, then download its JSON.
4. Copy that JSON privately onto the Pi, readable by `onespace-hub`, with
   owner-only permissions. For example, store it at
   `/var/lib/onespace-hub/google-desktop-client.json`, owner `onespace-hub`,
   mode `0600`. Do not paste it or tokens into chat or commit them.

Only `https://www.googleapis.com/auth/drive.file` is requested. This permits
OneSpace-created files; the app does not list or delete unrelated Drive files.
Your ordinary browser/Google app can still access your account normally.
Google organizational restrictions may block consent. Refresh tokens for an
external app left in **Testing** generally expire after seven days for this
scope; use the appropriate production consent configuration for durable use.
Google may still require reauthentication or revoke credentials later.

## 5. Connect your account locally

Stop the hub first: CLI operations use its exclusive metadata lock. If you
have a browser on the Pi, run:

```sh
sudo -u onespace-hub /opt/onespace-hub/bin/onespace-hub drive-connect \
  --data /var/lib/onespace-hub \
  --oauth-client /var/lib/onespace-hub/google-desktop-client.json
```

Open the sign-in URL printed in your **local terminal** and complete Google
consent. The callback listens only on Pi loopback port 53682 for five minutes.
Do not share the URL. The flow uses state verification and PKCE.

For a headless Pi, first open an SSH session **from the PC browser's machine**:

```sh
ssh -L 53682:127.0.0.1:53682 YOUR_PI_USER@YOUR_PI_ADDRESS
```

Run the same `drive-connect` command inside that session, then open its URL
in the PC's browser. The loopback callback travels through SSH. Do not open
53682 on your router or bind the callback publicly. If the port is occupied,
choose a different `--oauth-port` and match both SSH tunnel ports.

The refresh credential is saved on the Pi as an owner-only file; it is never
returned to Windows/Android. A protected filesystem is still necessary because
anyone who compromises the Pi account can read its files. This preview does
not provide end-to-end encryption against Google or a compromised Pi.

## 6. Grant cloud permissions explicitly, retaining your current tokens

While the hub is stopped, replace `phone` / `windows` with your existing IDs:

```sh
sudo -u onespace-hub /opt/onespace-hub/bin/onespace-hub permissions \
  --data /var/lib/onespace-hub --id phone \
  --scopes clipboard,media,camera,cloud,recording
sudo -u onespace-hub /opt/onespace-hub/bin/onespace-hub permissions \
  --data /var/lib/onespace-hub --id windows \
  --scopes clipboard,media,camera,cloud,recording
```

These commands replace the selected device's scope list, preserve its existing
token, and do not revive revoked devices. Include every old scope you wish to
keep. `cloud` permits managing the shared OneSpace Drive files; recording
control additionally requires both `camera` and `recording`. Grant the minimum
permissions each device needs. Existing devices gain no new scopes silently.

```sh
sudo systemctl daemon-reload
sudo systemctl start onespace-hub.service
sudo systemctl start onespace-mediamtx.service
```

Check `journalctl -u onespace-hub -u onespace-mediamtx` locally if startup fails.
The hub's source address/certificate/device-token checks still apply. Pair it
through your LAN or private overlay as described in START-HERE.md.

## 7. Use it in OneSpace

- Windows: launch `bin/OneSpace-Windows-v0.8.0-Drive-Preview.exe`, keep your
  existing profile, configure/verify the hub, then open **Cloud & recordings**.
- Android: build/install a correctly signed compatible update in Android
  Studio; open **Pi Hub → Cloud storage & recordings** and unlock.
- Press Refresh to verify your connected Google email, quota and file access.
  Merely having a saved credential is not proof current Google access works.
- Upload a test file or create a note; it should appear in the app-created
  `OneSpace` folder and in the file list. Open it in Drive to check it.
- Choose Temporary/Permanent and temporary days. Start recording, then refresh
  status. An enabled MediaMTX setting is not proof of frames: check new playable
  MP4 clips arriving in Drive. Stop recording explicitly when finished.
- You can keep a temporary file permanently or set a permanent file to expire.
  Moving to Trash requires a user confirmation. Expiry is automatic while the
  hub and Google access work, with periodic cleanup and retries after outages.
- File upload is foreground-only in this preview. Android pauses/cancels on
  leaving the protected screen and asks before large metered-data uploads.
  Select the same source again to resume. Temporary sessions can expire at
  Google; the app then restarts safely with the same allocated remote file ID.

## Storage, speed and limits

- 15-second MP4 target segments, cut on keyframes. Rotation is approximate.
  The current segment is uploaded after completion, not byte-for-byte live.
- File upload uses 1 MiB chunks, with a single recording uploader. Large user
  files are never staged completely on the Pi. Video uses the bounded buffer.
- At 5 Mbit/s, continuous footage is about **54 GB/day** before overhead. It
  needs sustained upload bandwidth above that bitrate. 5 TB is about 92 days
  at that rate **before other usage and Trash**, not unlimited recording.
- Temporary cleanup moves files to Drive Trash. It does not immediately free
  quota. Google normally removes Trash after 30 days; empty it yourself when
  needed. OneSpace does not permanently purge your Drive Trash automatically.
- Uploads use HTTPS; hub clients use pinned TLS. Recording checksums are checked
  against Drive before local deletion. Google can read ordinary uploaded MP4s;
  storage is not an opaque end-to-end encrypted vault.
- Internet loss/expired sign-in/full Drive pauses progress. Completed clips
  remain locally until verified, then are removed. The buffer cannot retain an
  indefinite outage; capture pauses and gaps are visible/expected.
- Power loss may leave the current segment unfinalized. It is not automatically
  uploaded or silently discarded. Inspect/repair it locally with media tools;
  do not mark arbitrary partial files complete. Completed clips remain queued.
- No Drive cloud relay for instant clipboard/live video: existing direct/hub
  text and WebRTC paths remain separate.
- Test on your Pi and account before relying on this for CCTV. This has not
  been deployed to your hardware or signed with your Android release key.

To disconnect, stop the hub and run `onespace-hub drive-disconnect --data
/var/lib/onespace-hub` as `onespace-hub`; this revokes the Google grant and
removes the saved credential. It does not delete your Drive files. If Google
cannot be reached, revoke OneSpace in your Google Account and secure the local
credential file until you can complete cleanup. Reconnecting a different
account is not an automatic migration of this account's root folder/jobs.
